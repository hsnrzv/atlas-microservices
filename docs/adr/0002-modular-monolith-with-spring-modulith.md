# ADR-0002: Modular monolith with Spring Modulith in repository `atlas-microservices`

- Status: Accepted
- Date: 2026-11-12
- Deciders: @hsnrzv (owner)

## Context

Atlas is a private personal planning application. The first deployment has one user. The business
capabilities (profile, onboarding, Ikigai areas, goals, finance, capacity, dashboard, later domain
extensions and AI) are strongly related: a goal affects finance and capacity views, and the dashboard
aggregates all of them. `project-instruction.md` §2.3 and §0.4 rule out microservices, Kafka and
per-domain services for the MVP. §11.1 asks for a modular monolith with logical boundaries, optionally
verified with Spring Modulith.

The GitHub repository was created as `hsnrzv/atlas-microservices` before this decision. The owner
decided on 2026-11-12 to keep the name and document that it is historical.

## Decision

- The backend is **one deployable Spring Boot application** (artifact `atlas-backend`, base package
  `dev.myatlas`) built from the repository `atlas-microservices`. The repository name is historical;
  the README states that it is not a microservice system.
- Each business capability is an **application module**: a direct sub-package of `dev.myatlas`
  (`profile`, `onboarding`, `ikigai`, `goals`, `finance`, `capacity`, `dashboard`; later the domain
  extensions and `ai`). Modules are created only when their first feature is implemented. No empty
  packages for future modules.
- **Spring Modulith 2.1.x** defines and verifies the boundaries:
  - `ModularityTests` runs `ApplicationModules.of(AtlasApplication.class).verify()` on every build:
    no cycles between modules, and no access to another module's internal packages.
  - A module's base package is its published Java API (facade interfaces, query DTOs, events).
    Sub-packages (`api` = REST adapter, `application`, `domain`, `infrastructure`) are internal.
    Additional exposed packages need an explicit `@NamedInterface`.
  - Allowed dependencies are declared per module with `@ApplicationModule(allowedDependencies = ...)`
    as listed in `docs/architecture/DOMAIN-MODULES.md`.
  - `shared` (cross-cutting value types such as money, time, owner identity, error model) is the only
    `Type.OPEN` module and must not contain business rules.
  - Module documentation is generated by Spring Modulith's `Documenter` into `target/` during the
    build. It is not committed.
- Modules communicate through published APIs and in-process Spring application events. A transactional
  outbox / Spring Modulith event publication registry is added only when a consumer needs guaranteed
  delivery (§8.3).
- Each module owns its tables (see ADR-0004). No module reads another module's tables or repositories.

## Consequences

- One build, one image, one database connection pool, one deployment: low operating cost and simple
  local development.
- Boundaries are enforced by tests, not by network calls. A boundary violation fails `./mvnw verify`.
- Refactoring across modules stays a normal code change. A module can still be extracted later because
  it already talks to others only through its API and events.
- The whole application scales and fails as one unit, which is acceptable for a personal application.
- Developers must understand Spring Modulith conventions: base package = API, sub-packages = internal.
  Package-private visibility is used where possible to make this visible in the IDE.

## Alternatives considered

- **Microservices per domain:** independent deployability is not needed. It would multiply
  infrastructure cost, data consistency problems and operational work. Explicitly excluded by §2.3.
- **Unstructured monolith (layer-first packages):** fastest to start, but boundaries erode and
  domain extensions would leak into the core goal model. No automated check.
- **Maven multi-module build per domain:** gives compile-time boundaries, but costs more build
  configuration and makes refactoring harder. Spring Modulith checks the same rules at test time and
  also documents them. It can be reconsidered if a module needs a separate release cycle.
- **ArchUnit rules only:** possible (Spring Modulith uses ArchUnit internally), but every rule would
  have to be written by hand, and there would be no module documentation or module integration tests.
