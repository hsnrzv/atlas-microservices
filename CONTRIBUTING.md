# Contributing to atlas-backend

Thanks for helping build IKIGAI ATLAS. This repository is the Spring Boot modular monolith
(`atlas-microservices`; see the [README](README.md) for the naming note).

## Workflow (trunk-based)

1. `main` is always releasable. Never push directly to `main`; every change goes through a pull request.
2. Branch from the latest `main` with a short-lived branch (merge within a few days):
   - `feat/<short-topic>`: new behaviour
   - `fix/<short-topic>`: bug fixes
   - `docs/<short-topic>`: documentation and ADRs only
   - `chore/<short-topic>`: build, CI, dependencies, tooling
3. Keep PRs small and reviewable: one backlog item from [PLAN-BACKEND](docs/plan/PLAN-BACKEND.md) or
   [PLAN-DATABASE](docs/plan/PLAN-DATABASE.md) per PR where possible.
4. Rebase on `main` before merging; prefer squash merges with a Conventional Commit title.

## Commit messages ([Conventional Commits 1.0](https://www.conventionalcommits.org/en/v1.0.0/))

```text
<type>(<optional scope>): <imperative summary>

<optional body: what and why>

<optional footer: BREAKING CHANGE: ..., Refs: #123>
```

Types: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`. Use the module as the
scope when it applies, e.g. `feat(goals): add goal node completion`, `build(deps): bump spring-boot`.
Mark breaking API or schema changes with `!` (`feat(api)!: ...`) and a `BREAKING CHANGE:` footer.

## Local checks before opening a PR

```bash
export JAVA_HOME=<path to JDK 25>
./mvnw verify          # needs Docker for the Testcontainers integration tests
```

`./mvnw verify` must pass locally with Docker running. CI runs the same command and fails if the
integration tests were skipped.

## Code rules

- **Module boundaries:** each business capability is a top-level package under `dev.myatlas`
  (`dev.myatlas.goals`, ...). Other modules may only use a module's published API (base package or
  named interfaces) and its events. `ModularityTests` enforces this. Do not create empty packages for
  future modules. See [DOMAIN-MODULES](docs/architecture/DOMAIN-MODULES.md).
- **Layering inside a module:** `api` (controllers, DTOs) → `application` (use cases, transactions,
  authorization) → `domain` (entities, value objects, rules) ← `infrastructure` (JPA, adapters).
  Never expose JPA entities over REST.
- **Database:** every schema change is a new Flyway migration; follow the
  [migration rules](src/main/resources/db/migration/README.md). Never edit an applied migration.
- **API:** follow [API-CONTRACT](docs/architecture/API-CONTRACT.md) (paths, Problem Details, money and
  date formats, pagination, optimistic locking). Breaking changes need a new version or a written
  compatibility plan.
- **Privacy:** never log financial amounts, notes, health measurements, tokens or full request bodies.
  No personal sample data in code, tests or migrations.
- **Dependencies:** add a dependency only with a concrete use, a current release and an acceptable
  license; record it in [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md).
- **Decisions:** material architecture decisions get an ADR in [docs/adr](docs/adr/README.md)
  (copy `0000-template.md`, next free number, status `Proposed` until accepted).
- Formatting follows [.editorconfig](.editorconfig) (tabs for Java and `pom.xml`, as generated by Spring
  Initializr).

## Pull request checklist (Definition of Done)

The [pull request template](.github/pull_request_template.md) contains the Definition of Done from
`project-instruction.md` §19. A PR is ready to merge only when every applicable item is checked:

- Acceptance criteria are met and demonstrated.
- Code follows repository and module boundaries.
- No business logic is duplicated in UI and backend.
- Automated tests cover the behaviour and important edge cases.
- API and database changes are versioned and documented.
- Security/privacy implications are considered.
- CI passes, and no new critical/high vulnerability is ignored without a documented exception.
- No secrets or personal sample data are committed.
- README/plan/ADR updates are made where needed.
- The PR summary explains changes, tests, migration steps, and known limitations.

## Reporting security issues

Do not open public issues for vulnerabilities. See [SECURITY.md](SECURITY.md).
